- `BenefitAccrualService::accrue()`'s `updateOrCreate()` match and `calculate()`'s prior-period (carry-forward) lookup both had their `is_voided = false` filters removed. `ReimbursementController::linkToBenefitPeriod()`'s period match had the same filter removed. `MemberController::show()`'s `$currentBenefitPeriod`/`$currentCyclePeriod` and `generateBenefitPeriod()`'s "already exists" check all had their `is_voided` filters removed — every one of these is back to exactly what it was before §2.11, since the column they were filtering on no longer exists.
- **Database — handled carefully, per "preserve existing data":** the original §2.11 migration's first run had already failed partway through in this environment (MySQL error 1553 dropping the old unique index) — and since MySQL's `ALTER TABLE` statements auto-commit individually rather than as one transaction, the column/FK additions that ran *before* that failure may already be sitting in the live database even though the migration itself was never recorded as completed. To handle that safely regardless of which partial state the DB is actually in:
  1. Rewrote `2026_09_24_100000_add_void_fields_to_benefit_periods_table.php` (same file, same timestamp — it was never recorded as having run) to be fully idempotent: every column/index add or drop now checks first via `Schema::hasColumn()`/`Schema::getIndexes()`, so it safely finishes to a known state (void columns present, old unique dropped) whether it previously ran fully, partially, or not at all.
  2. Added a new migration, `2026_09_24_200000_revert_void_fields_from_benefit_periods_table.php`, that undoes it: restores the `unique(member_id, from_date, to_date)` constraint (this IS the strict one-per-cycle rule at the DB level — no void, delete, or regenerate can ever get around it once it's back), then drops `is_voided`/`voided_at`/`voided_reason`/`voided_by` and their supporting index/FK. Also idempotent throughout, and index-ordering-safe (adds the unique back before dropping the plain index that was standing in as the FK's backing index — the same MySQL 1553 issue in reverse).
  3. **Duplicate handling:** if any member was actually voided-then-regenerated while this feature was live, they'd now have two rows sharing the same `member_id`/`from_date`/`to_date` — which would make restoring the unique constraint fail. The revert migration only removes a voided row when a confirmed ACTIVE sibling exists for the exact same member+cycle (a genuinely superseded, abandoned row); a voided row with no active sibling is left completely untouched and simply becomes an ordinary row once `is_voided` is dropped — correctly blocking that cycle from regeneration under the new strict rule, same as if Void had never existed. Any other ambiguous case (e.g. two rows both still voided) is deliberately left alone rather than guessed at, so the unique-constraint step fails loudly with a clear DB error instead of silently discarding data.

### 2.12 Dependent eligibility now waits for the next benefit period
- **Business rule changed (intentional):** adding a dependent no longer raises the member's GHP amount immediately. Previously, `DependentController::store()` recalculated `members.ghp_amount` the instant a dependent was saved, based only on the age/relation rule (`Dependent::is_eligible`) — no awareness of *when* it was added. Now a dependent added during an ongoing benefit period is recorded and shown right away, but only starts counting toward the higher (₱4,200) rate once the *next* coverage cycle begins.
- **How it works:** `dependents` gets two new nullable columns, `date_added` and `eligibility_date`. `DependentController::store()` sets `date_added` = today and `eligibility_date` = the start of the *next* coverage cycle (via new `BenefitAccrualService::resolveDependentEligibilityDate()`, which reuses the existing `coveragePeriod()` Apr–Mar/Jun–May logic). `BenefitAccrualService::resolveGhpAmount()` now takes an optional `$asOf` and checks each dependent through new `Dependent::isGhpEligibleAsOf($asOf)` (age/relation rule AND, if set, `$asOf >= eligibility_date`) instead of the age rule alone. `calculate()` passes its own `$asOf`; `requiredAmountForCycle()` evaluates at the cycle's own end date, since eligibility is an all-or-nothing-per-cycle rule, not a daily one.
- **Nothing retroactive, nothing backfilled on purpose:** `eligibility_date` is left `NULL` for every dependent already on file, and for any dependent created directly via Eloquent rather than through the real "Add dependent" form (tests, factories, `ImportLegacyGhpData`). `isGhpEligibleAsOf()` treats `NULL` as "not time-gated" — always eligible, exactly like before this change. Only dependents added through the app from now on get the pending-until-next-cycle treatment. No migration backfill was needed as a result.
- **Why no `benefit_period_id` FK on Dependent:** eligibility is purely calendar/cycle-boundary math (same Apr–Mar/Jun–May logic as everything else), independent of whether a `BenefitPeriod` row has actually been generated yet for that cycle — linking to a specific row would have created null-period edge cases for no benefit.
- **UI:** Dependents table on the member page now shows Date added, a Status badge (Eligible / Pending Eligibility / Not eligible), and Eligible period columns, plus a note on the Add/Edit dependent modal.
- **One existing test intentionally changed:** `MemberBenefitSetupTest::test_adding_an_eligible_dependent_after_saving_recalculates_ghp_amount_without_resetting_dates` asserted the *old* (now-incorrect) immediate-bump behavior — replaced with `test_adding_a_dependent_mid_cycle_does_not_immediately_raise_the_ghp_amount` plus a companion test proving the same dependent becomes eligible once evaluated in the next cycle. All other dependent-touching tests (`AmountAdjustmentManagementTest`, `BenefitAccrualServiceTest`'s existing cases) create dependents directly via Eloquent, so they're unaffected by the `NULL`-safe default.
- **Files:** migration `2026_09_24_110000_add_eligibility_fields_to_dependents_table.php`, `Dependent.php` (`date_added`/`eligibility_date` casts+fillable, `isGhpEligibleAsOf()`, `eligibility_status` accessor), `BenefitAccrualService.php` (`resolveGhpAmount($asOf)`, `resolveDependentEligibilityDate()`, `calculate()`/`requiredAmountForCycle()` updated), `DependentController::store()`, `members/show.blade.php` (Dependents table + modal hint).
- **Tests:** `MemberBenefitSetupTest.php` (updated + new), `BenefitAccrualServiceTest.php` (new: eligibility-date calculation for both member types, gating before/after the date, multiple-pending-dependents, `NULL`-eligibility-date safety net).

### 2.16 Dependent becomes eligible -> GHP amount AND Available balance follow (prorated by months rendered)
- **Gap found:** the Benefit balance card reads the STORED `benefit_periods` row. §2.14's Immediate Eligibility only synced `members.ghp_amount` and deliberately left that row alone, so the card stayed at ₱3,600 / ₱1,800 after a dependent became eligible.
- **Fix (recompute, never add a delta):** new `BenefitAccrualService::refreshCurrentPeriodIfAmountChanged()` re-runs the existing `accrue()` for the current cycle's ALREADY-GENERATED period, but only when the eligible-dependent outcome changed its GHP amount. `accrue()` is the existing formula `ghp_amount / 12 x months rendered` (+ carry-forward, − used from actual reimbursements), so 3,600 -> 4,200 with 6 months rendered gives 1,800 -> 2,100 (+300 = 600 / 12 x 6) with no new calculation path. Deductions are re-summed from reimbursements (preserved); prior periods are never touched; no period is ever created, reopened, voided or deleted (one-per-cycle rule intact).
- **No duplicates:** because it recomputes and no-ops when the stored amount already matches (returns null, writes nothing), repeating the grant, refreshing the page, or saving other member changes cannot re-add the benefit. `MemberController::show()` is read-only.
- **Single entry point:** new `DependentEligibilityService::recalculateBenefit()` (transaction: `syncGhpAmount()` + the refresh above). Used by `grantImmediate()` (so the Edit Member "Immediate" spouse path gets it too) and by `DependentController::store()/update()/destroy()`; the controller's private `syncGhpAmount()` was removed. ### 2.21 Dependent benefit increase covers outstanding excess GHP
- **Trigger:** a dependent becoming eligible (Immediate Eligibility — a normally added dependent is pending until the next cycle and changes nothing) goes through `DependentEligibilityService::recalculateBenefit()` → `BenefitAccrualService::refreshCurrentPeriodIfAmountChanged()`, inside a transaction. That method already does nothing when the period's GHP amount already matches, which is the guard against applying the same increase twice (page refreshes, dependent edits and repeat recalculations all find nothing to do).
- **The increase** = the actual growth of the fund, not the recalculated balance: the same months rendered priced at the new amount minus the old one (10 months: 10 x 350 - 10 x 300 = 500; 3 months: 3 x 350 - 3 x 300 = 150). Ordinary monthly accrual since the period was last refreshed is NOT counted.
- **Applied** by `BenefitAccrualService::applyFundIncreaseToExcess()` to the member's active (non-voided) claims of that period that still have excess, oldest first (OR date, then id), never more than the increase and never more than each claim's remaining excess (A 300 + B 500 with a 500 increase -> A 0, B 300). The rest simply stays in Available GHP. The claim keeps its id and full OR amount; no reimbursement or transaction row is created.
- **Stored on the reimbursement** (migration `2026_09_30_120000`): `original_excess_amount` (excess when filed/edited), `excess_covered_amount` (covered so far) and the existing `excess_amount`, which is now the REMAINING excess (original - covered), so every red marking, export and email already shows the outstanding amount. Existing rows are backfilled original = current excess. Editing a claim recalculates the original excess from its recorded Available GHP and keeps what was already covered.
- **Used is not increased:** `calculate()` reports the covered part separately (`excess_covered`) and subtracts it from `used`. Available is unchanged: `fund - min(claimed, fund)` is the same number as `fund - used - covered`. Example (10 months): claim 3,750 on 3,000 available -> excess 750, used 3,000, available 0; dependent added (fund 3,500) -> covered 500, remaining 250, used still 3,000, available 0. Claim 3,200 (excess 200) -> covered 200, remaining 0, available 300, used 3,000.
- **Not reversed:** removing a dependent later lowers the fund again but does not un-cover excess (documented limitation). An excess is only ever covered by a dependent-driven increase, not by ordinary monthly accrual.
- **Shown:** member page + records page (remaining in red while > 0, "original / covered" note, totals), receipt PDF (Original / Covered / Remaining Excess GHP), report PDF, email body, CSV (`Original Excess`, `Excess Covered`, `Excess Deduction` columns).

### 2.29 Adjust GHP amount covers outstanding Excess GHP (same rule as an eligible dependent) and is reversible
- **Rule:** raising a member's GHP amount is treated exactly like a dependent becoming eligible (§2.21): the actual **fund increase** first covers the member's outstanding Excess GHP, oldest claim first, and only what is left stays in Available GHP. There is ONE calculation, not two: `AmountAdjustmentService::apply()` uses `BenefitAccrualService::fundIncrease()` + `applyFundIncreaseToExcess()` (the same methods the dependent flow uses; `refreshCurrentPeriodIfAmountChanged()` gained optional `$asOf`/`$source` parameters, `applyFundIncreaseToExcess()` an optional `$source`). The dependent flow passes no source and behaves exactly as before.
- **The increase is the fund's growth, not the annual difference:** months rendered × new rate − the same months × old rate. With 10 months rendered, 3,600 → 4,200 is **+500** (it is +600 only once all 12 months are rendered; with 6 months it is +300). `covered = MIN(increase, outstanding excess)`; `remaining excess = outstanding − covered`; `to Available = increase − covered`. A **decrease** never covers anything (and records 0, never a negative, as "to Available").
- **Nothing else changes:** Used GHP (`calculate()` reports the covered part separately and subtracts it from used), the reimbursement's `or_amount`, `original_excess_amount` and every other claim/period are untouched. Available is recomputed by the normal engine, never overwritten.
- **Tracked separately from the original excess:** each adjustment row (`benefit_amount_adjustments`) stores `kind`, `increase_amount`, `outstanding_excess_before`, `excess_covered_amount`, `excess_remaining_after`, `available_increase_amount`, `reverted_at/by` (all nullable, NULL for legacy rows). Each claim it touched is a row in the new **`excess_coverages`** ledger (member, reimbursement, adjustment, amount, `reversed_at`) — so the part covered by an *adjustment* is distinguishable from a dependent-driven cover on the same claim (the claim shows "of which ₱X covered by GHP adjustment").
- **Revert ("Revert to automatic")** restores exactly the not-yet-reversed ledger rows (`excess_amount += amount`, `excess_covered_amount −= amount`), stamps them `reversed_at` (never deleted), marks the adjustment(s) reverted, switches back to the automatic amount (3,600/4,200) and recomputes the period — so Available returns to its pre-adjustment value. It never infers anything from current balances: a claim filed afterwards, or a cover from another source, is left alone (tested: other 100 covered by something else stays covered). A second revert is a no-op. A `kind='revert'` history row records what was restored.
- **Idempotent:** the increase is relative to the CURRENT amount read under a member row lock, and `refreshCurrentPeriodIfAmountChanged()` no-ops when the period already matches — so a page refresh, re-opening the member, or submitting the same adjustment twice covers nothing more (tested through the real route). Everything is one transaction.
- **Inactive members:** rejected by the `member.active` route middleware AND by the service itself (checked on the locked row; the controller turns it into a notice). Non-admins get 403.
- **UI:** Amount adjustment history gained an Excess GHP column (increase / covered of excess / remaining excess / to Available; "restored" on a revert row) and a Status badge (Active / Reverted / Revert); the Excess Deduction cell on a claim shows the part covered by a GHP adjustment; the Adjust modal explains the rule.
- **Deliberate limits (decide if you want them changed):** (1) **single override:** a member has ONE current manual amount, so "Revert to automatic" undoes the whole chain of adjustments at once. **Update: reverting just the latest active adjustment is now possible too — §2.31.** (2) As with dependents, nothing is covered when **no benefit period is generated yet** for the current cycle (the increase can't be measured; the adjustment still saves, with NULL increase). (3) Reverting a **decrease** doesn't cover excess. (4) A dependent-driven cover is still not individually revertible (unchanged, §2.21).
- **Migrations:** `2026_10_07_100000_add_excess_tracking_to_benefit_amount_adjustments_table`, `2026_10_07_100001_create_excess_coverages_table`, `2026_10_08_100000_backfill_legacy_amount_adjustment_kinds` (relabels old "Reverted to automatic" rows as `revert` and marks earlier adjustments reverted; data only, safe to re-run). ### 2.30 Coverage Year History: Cancel replaced by Revert (Claim | Revert)
- **What the old Cancel actually did (inspected first):** nothing beyond the status. Claim only sets `claimed_at` / `claimed_by`; Cancel just blanked them, leaving no record on the period of who undid it or when (only the dirty-field activity-log line), and Claim could then be used again. Claim reads and changes no GHP figure, reimbursement, excess GHP, dependent or other period (§2.28), so **there is no balance, excess or transaction effect to unwind** — the status is the whole of what a claim does. The lifecycle has exactly two states, Unclaimed / Claimed; no status column exists and none was added.
- **Revert is NOT a renamed Cancel.** It is a confirmed, recorded, once-per-claim action: `Unclaimed --Claim--> Claimed --Revert--> Unclaimed (marked Reverted)`.
  - Allowed only while the period is **Claimed**. Refused on the server for a never-claimed period ("This Benefit Period has not been claimed, so there is nothing to revert.") and for an already-reverted one ("No further revert is available for this Benefit Period."). Reverting the *generation* of a period is deliberately not offered: the strict one-period-per-cycle rule (§2.13) removed void / delete / regenerate, so an unclaimed period has nothing to revert.
  - Stamps `reverted_at` / `reverted_by` on the period (the table shows a **Reverted** badge on an Unclaimed period), and writes **one explicit audit entry** (activity log `benefit_period`: action "Revert Benefit Period", member, member code, coverage year, period dates, previous status Claimed, new status Unclaimed (Reverted), who, when). The model's own dirty-field logging is suppressed for the call so there is exactly one entry, not several.
  - **Never deletes the period**, never touches another period, another member, any GHP amount / Used / Available, any reimbursement or its excess (original / covered / remaining), any `excess_coverages` ledger row, any dependent or any GHP amount adjustment. (It is unrelated to "Revert to automatic" on a GHP amount adjustment, §2.29 — that one restores covered excess from its ledger; this one has nothing of that kind to restore, because Claim never changed any excess.)
  - After a revert the period can be **Claimed again** (existing behavior kept); that starts a fresh claim, clears the Reverted marker (the earlier revert stays in the activity log), and the new claim can itself be reverted once.
- **Transaction-safe:** one `DB::transaction`, row lock on the period, state re-validated under the lock, status write + audit entry together — any failure rolls the whole thing back (a test makes the audit write throw and asserts the period is still Claimed with no revert marker). A double click, second admin, page refresh or direct POST can't revert twice.

### 2.31 Revert a single GHP amount adjustment (latest active first) — "revert only #2, #1 stays intact"
- **Why:** §2.29 only offered "Revert to automatic", which undoes every active adjustment at once, so with two stacked adjustments (+300 then +200) you couldn't reverse just the second. The adjustment spec asks for exactly that ("Only Adjustment #2's ₱200 effect is reversed. Adjustment #1 must remain intact."), and the data to do it already existed: each adjustment has its own ledger rows (`excess_coverages.benefit_amount_adjustment_id`) and its own `old_amount`. No migration.
- **What it does** (`AmountAdjustmentService::revertAdjustment()`, one transaction, member + adjustment rows locked, state re-checked under the lock): restores to their claims **only that adjustment's** not-yet-reversed ledger rows (`excess_amount += covered`, `excess_covered_amount −= covered`, rows stamped `reversed_at`, never deleted); marks the adjustment reverted (who/when); puts the member's amount back to **what it was before that adjustment** (its `old_amount`) — or, if it was the only active adjustment, releases the manual override and recomputes the automatic 3,600/4,200 from current dependents; recomputes the current period (Available is derived, so exactly the increase that adjustment had added disappears — the part that had gone to Available, and none of the part that had covered excess); writes a `kind = revert` history row (amount restored, reason naming the adjustment). The same restore routine (`restoreCoverages()`) now backs both this and "Revert to automatic", so the two can't drift.
- **Worked example (the fixture the tests use):** member with fund ₱3,000, one claim ₱3,750 (original excess ₱750). Adjustment #1 3,600 → 3,960 (+300) covers 300 → excess 450. Adjustment #2 3,960 → 4,200 (+200) covers 200 → excess 250, covered 500. **Revert #2** → excess **450**, covered **300**, original still 750, OR amount still 3,750, member back on **3,960** (manual), #1 still Active with its ledger row untouched. Then reverting #1 → excess 750, covered 0, override released (3,600).
- **Only the latest active adjustment can be reverted on its own.** Each adjustment's `old_amount` is the previous one's `new_amount`, so reverting an earlier one underneath a later one has no defined result; it is refused ("Only the most recent active GHP amount adjustment can be reverted. Revert the later adjustment first, or use \"Revert to automatic\" to undo all of them.") rather than guessed. Also refused with a message: an already-reverted adjustment (never restores twice, no extra history row), and a `revert` history row. A claim filed after the adjustment, an earlier adjustment's cover and a dependent-driven cover on the same claim are never disturbed (tested).
- **Backend rules:** route `members.amount-adjustments.revert` (POST `/members/{member}/amount-adjustments/{adjustment}/revert`) in the admin group (403 otherwise; guests to login) and behind `member.active` (a deactivated member is rejected before the controller runs; the service re-checks on the locked row too); an adjustment id from another member's page is a 404.
- **UI:** the Amount adjustment history table gets an **Action** column (admins): the latest active adjustment has a live **Revert** (confirm prompt, button locks on submit); other active rows show it disabled with the reason; reverted / revert rows show nothing; everything is disabled for a deactivated member. "Revert to automatic" in the Benefit balance card is unchanged.
- **Files:** `AmountAdjustmentService.php` (`revertAdjustment()`, `restoreCoverages()`; `revertToAutomatic()` now calls the helper), `AmountAdjustmentController.php` (`revert()`), `routes/web.php`, `members/show.blade.php`, `tests/Feature/AmountAdjustmentIndividualRevertTest.php` (new).
- **Tests:** revert #2 of two leaves #1 intact; reverting #1 afterwards returns to the original state; an earlier adjustment can't be reverted under a later one (nothing changes); only adjustment → original excess restored + override released; no-excess adjustment → its Available increase removed, Used GHP untouched; adjustment greater than the excess → leftover Available removed and excess restored; a later claim and another source's cover survive; second revert refused with no extra row or restore; revert row not revertible; "Revert to automatic" after an individual revert restores nothing twice; rollback when a restore fails mid-way; inactive member rejected (service and route); non-admin 403, guest to login, another member's adjustment 404; real route once, repeat changes nothing; button only on the latest active row, disabled for a deactivated member, absent for non-admins.

### 2.32 Multiple reimbursement RECORDS per coverage year (Filed / Claimed / Reverted), Claimed records are locked
- **Found already built (code, migration, view and tests) but never logged here** — the code and tests already cite "task.md §2.32". This entry was written after verifying each piece against the files; nothing below was re-implemented.
- **Rule:** a member may file again after a reimbursement has been Claimed, as long as Available GHP is positive. Every filing is its own **Record #n** under its coverage year; a Claimed record is never reused, edited or voided, and no later GHP increase covers its excess. The Available GHP rule itself is unchanged (positive balance needed; the amount may exceed it and the excess is recorded on that record).
- **Design decision — where "a new Benefit Period History record" lives:** the *record* is the reimbursement row, NOT a second `benefit_periods` row. A coverage cycle keeps exactly one `benefit_periods` row (the GHP fund: amount / used / available) and the unique index `(member_id, from_date, to_date)` is untouched. Splitting the fund into several period rows per cycle would have counted the same accrual and reimbursements more than once and broken the §2.13 / §2.27 one-per-cycle guarantees, so "Record #1 / #2 / #3 in 2026–2027" are reimbursements grouped under that one period (`Reimbursement::recordNumber()` = filing order within the period; voided records keep their number). No `member_id + coverage_year` uniqueness exists or was added.
- **State** (one source of truth, no new status column): `reimbursements.claimed_at / claimed_by` and `reverted_at / reverted_by`. Filed = never claimed; Claimed = `claimed_at` set (**locked**, `Reimbursement::isLocked()` = claimed and not voided); Reverted = unclaimed with `reverted_at` set (unlocked, can be claimed again). The old per-period claim columns on `benefit_periods` (§2.28 / §2.30) remain in the table as history only and are no longer read or written.
- **Claim | Revert (`ReimbursementClaimController`, routes `members.reimbursements.claim` / `.revert`, admin + `member.active`):** acts on ONE record only; state re-checked under a row lock inside a transaction (a double click, stale page or second admin can't double-claim / double-revert); a voided record can be neither; the record must belong to the `{member}` in the URL (404 otherwise); one explicit activity-log entry per action. Neither action reads or changes any amount, the fund, excess figures or another record. Revert unlocks the record and covers nothing retroactively — only FUTURE increases may reach its excess.
- **The lock, enforced in the engine:** `BenefitAccrualService::applyFundIncreaseToExcess()` filters `->notVoided()->unclaimed()`. Both a GHP amount adjustment and a dependent becoming eligible go through it, so neither can touch a Claimed record's excess; with several records only the eligible (Filed / Reverted) ones receive the cover, oldest first, and the remainder stays in Available GHP. `AmountAdjustmentService::apply()` snapshots `outstanding_excess_before` from unclaimed records only, so a locked record's excess doesn't inflate the "remaining excess" figure either. The reimbursement is also protected directly: `ReimbursementController::update()` and `void()` re-check `isLocked()` under a lock and refuse with `LOCKED_MESSAGE`, whatever the page showed.
- **Excess belongs to its own record:** `original_excess_amount`, `excess_covered_amount` and the remaining `excess_amount` live on each reimbursement (and, for adjustment covers, in the `excess_coverages` ledger keyed by reimbursement + adjustment). There is no member-level excess total anywhere.
- **Duplicate submissions:** the File reimbursement form generates a one-time `submission_token` each time it is opened (the Edit form sends none). `ReimbursementController::store()` checks it under the member row lock and BEFORE the balance check, returning the existing record with `DUPLICATE_MESSAGE` instead of filing again (so a repeat still works after the first filing used up the balance); a UNIQUE index on `reimbursements.submission_token` is the backstop (`UniqueConstraintViolationException` is caught → same message, transaction rolled back). The button also locks on submit, but that is only a convenience.
- **Atomic:** filing runs in one `DB::transaction` (lock member → duplicate check → available-balance check → insert); a failure leaves no reimbursement, no orphan period and no changed GHP figures (tested by forcing the balance lookup to throw).
- **UI (`members/show.blade.php`):** the Benefit periods table keeps one row per cycle (fund figures + "N records · M claimed"); below it a **Reimbursement records** table lists every record separately — Coverage year, Record #, OR date / no., Reimbursement, Excess, Status badge (Filed / Claimed / Reverted / Voided) and, for admins, **Claim | Revert** for that record only. Revert opens a confirmation modal. Edit / Void on the Reimbursements table are disabled for a Claimed record (with the reason as tooltip); everything is disabled for a deactivated member. Nothing asks the user to "create a new period" — filing again simply creates the next record.
- **Migration** `2026_10_09_100000_add_claim_record_fields_to_reimbursements_table.php` (idempotent): adds the five columns above; backfills existing data so it keeps its meaning — active reimbursements under a period that was Claimed become Claimed, under a period whose claim was Reverted become Reverted; voided and unlinked reimbursements are left alone; nothing is deleted or recreated and no amount changes.

### 2.35 Several Benefit Period RECORDS per coverage cycle (claim state on the record) — SUPERSEDES §2.32–§2.34
- **Spec (2026-10-12):** one Unclaimed Benefit Period record collects every reimbursement filed until it is **Claimed**; Claim locks that record only; the next reimbursement filed for the same cycle opens a NEW record (never created empty or in advance). Claim state belongs to the individual record, not the coverage year. A new record never grants a new entitlement.
- **This supersedes** the per-reimbursement claim design of §2.32–§2.34 (one `benefit_periods` row per cycle, `reimbursements.claimed_at`, `ReimbursementClaimController`, `ReimbursementRecordTest`, `_record_row`). Those files are parked in `_removed-by-claude/`; the `reimbursements.claimed_at / claimed_by / reverted_at / reverted_by` columns stay as history and nothing reads or writes them. It also replaces the strict "one period per cycle" wording of §2.13 / §2.27 for *records* (generation is still once per cycle: Generate and the bulk action refuse a cycle that already has any record).
- **Schema** (`2026_10_10_100000_support_multiple_benefit_period_records`, idempotent): `benefit_periods.record_no` (default 1, so every existing row is record 1); unique key becomes `(member_id, from_date, to_date, record_no)` (the old 3-column unique is dropped only after the new one exists). Backfill: a period becomes Claimed when it has active reimbursements and EVERY one was claimed; partly-claimed periods keep their state (admin must claim them). `down()` refuses while any cycle has several records.
- **Entitlement is never duplicated:** `BenefitAccrualService::calculate()` works on the CYCLE (amount, months, all reimbursements by OR date), so the fund / Available exist once. `accrue()` refreshes ONLY the open record: `ghp_amount` = the cycle's entitlement (same on every record), `ghp_used` = the cycle's used minus what earlier records hold (their own share), `ghp_available` = the cycle's remaining balance. It never creates record 2+. `BenefitPeriod::summarizeCycle()` is the one way to read "the cycle's figures" from several records (entitlement once, Used summed, Available from the last record).
- **Filing** (`ReimbursementController::store()` → `BenefitAccrualService::recordForFiling()`), one transaction under the member row lock: duplicate-token check → positive-Available check → the cycle's open record, or a new record (`record_no + 1`) only when every record is Claimed → insert. The reimbursement stays in its record for life (an edit never moves it unless the OR date moves to another cycle).
- **Claim | Revert** (`BenefitPeriodClaimController`, routes `members.benefit-periods.claim / .revert`, admin + `member.active`): keyed by the record's own id; member row lock then record lock (same order as filing, so a claim and a filing arriving together serialize); state re-checked under the lock. Claim is refused for a record with no active reimbursement (`NOTHING_TO_CLAIM`). Revert only for the cycle's LATEST record (`LATER_RECORD_EXISTS` otherwise) so a cycle never has two open records; the reverted record is the open record again. One explicit audit entry per action. Neither touches any amount, excess figure, reimbursement or other record.
- **Claimed = locked everywhere:** `Reimbursement::isClaimed()` is now derived from its record; edit / void / un-void are refused (`LOCKED_MESSAGE`); `applyFundIncreaseToExcess()` (GHP adjustment + dependent increase) skips excess on Claimed records; reverting an adjustment that covered a Claimed record is refused.
- **Fixed in this pass (found while checking the code against the spec):** (1) the member page referenced a `$historyRows` variable and `ReimbursementClaimController` routes/constants that no longer existed — it would have thrown; the Coverage Year History is rebuilt as ONE row per record (Period | GHP amount | Used GHP | Available GHP | Status | Claim / Revert) with each record's reimbursements listed under it. (3) `AmountAdjustmentService::apply()` measured the increase from record 1's frozen (stale) amount — it now uses the open record, or the member's amount before the change when every record is Claimed. (4) `refreshCurrentPeriodIfAmountChanged()` returns null when every record is Claimed (it would otherwise report a "change" on every call).
